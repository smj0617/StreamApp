# 여러 앱 인스턴스의 상태는 공유 볼륨의 SQLite와 Redis 채팅 중계에 둔다

과제 ⑤(로컬 오토스케일)에서 앱을 로컬 쿠버네티스(kind)에서 2~5개 파드로 늘리고 줄인다. 요청이 어느 파드로 가든 같은 답을 내고, 파드가 늘거나 줄어도 로그인·녹화방송·댓글·라이브가 그대로여야 한다. 그래서 인스턴스 메모리에만 있던 상태를 모두 인스턴스 밖으로 옮긴다.

| 상태 | ⑥까지 | ⑤ 여러 인스턴스 |
| --- | --- | --- |
| 사용자·채널·라이브·녹화방송·댓글·후원·로그인 세션 | SQLite 파일 | 그대로. 파일을 공유 볼륨(`/data`, PVC)에 둔다 |
| 녹화방송 영상 파일 | `data/recordings/` | 같은 공유 볼륨의 `/data/recordings/` |
| 휴대폰 송출 세션 → 채널(WHIP 종료 권한 확인) | 인스턴스 메모리(`HashMap`) | DB 표 `whip_sessions`(마이그레이션 0006) |
| 채팅 이벤트(메시지, 제목 변경, 라이브 종료) | 인스턴스 메모리의 tokio broadcast | 메모리 broadcast + Redis pub/sub 중계(`STREAMAPP_REDIS_URL`이 있을 때만) |

- **SQLite를 그대로 쓴다.** kind 클러스터의 노드가 하나라서 모든 파드가 같은 노드에 뜨고, ReadWriteOnce local-path 볼륨(노드의 폴더 하나)을 함께 마운트할 수 있다. 같은 커널·같은 파일 시스템이므로 SQLite의 파일 잠금과 WAL 공유 메모리가 프로세스(파드) 사이에서도 동작한다. 연결은 이미 WAL과 `busy_timeout`(5초)을 쓴다.
  - **동시 시작**: sqlx의 SQLite 마이그레이션은 잠금을 잡지 않는다(`lock()`이 아무것도 하지 않는다). 대신 마이그레이션 하나를 트랜잭션 하나로 커밋하므로, 두 파드가 같은 마이그레이션을 동시에 적용하면 한쪽은 오류로 되돌려진다. `db::connect_file`은 연결·WAL 전환·마이그레이션 전체를 잠시 뒤 다시 시도하고(최대 8번), 다시 시도한 쪽은 이미 적용된 마이그레이션을 건너뛴다. 기본 사용자 만들기는 `BEGIN IMMEDIATE`로 세기 전에 쓰기 잠금을 잡아 한 파드만 만든다. 별도 마이그레이션 Job을 두지 않은 이유: 매니페스트와 실행 순서가 늘고, ⑥ 단일 서버의 "시작할 때 마이그레이션" 동작과 갈라진다.
- **채팅은 Redis pub/sub로 중계한다.** 채팅은 저장하지 않으므로 DB에 넣지 않는다. 이벤트를 보내는 인스턴스는 자기 참여자에게 바로 보내고 같은 이벤트를 Redis 채널 `streamapp:chat:<채널ID>`에 올린다. 모든 인스턴스가 `streamapp:chat:*`를 구독해 다른 인스턴스(인스턴스 ID로 구분)가 올린 이벤트를 자기 참여자에게 보낸다. Redis에 닿지 못해도 앱은 멈추지 않고, 그 인스턴스 안의 채팅은 그대로 되며 다른 인스턴스로의 전달만 끊긴다(다시 연결한다). `STREAMAPP_REDIS_URL`이 없으면 지금처럼 메모리만 쓴다(⑥ 단일 VM).
- **라이브 상태는 이미 DB에 있다.** MediaMTX는 앱 Service 주소로 인증과 송출 시작·종료 훅을 보내므로 어느 파드가 받아도 DB에 반영된다. 다만 앱 시작 때의 송출 상태 맞추기는 "MediaMTX에 연결할 수 없으면 열린 라이브를 모두 닫는다"였다(단일 인스턴스에서 꺼져 있던 동안 놓친 종료 알림 보정). 여러 인스턴스에서는 스케일 아웃으로 뜬 새 파드가 MediaMTX에 잠깐 닿지 못했다는 이유로 진행 중인 라이브를 닫으면 안 되므로, `STREAMAPP_MULTI_INSTANCE=true`이면 연결할 수 없음을 "알 수 없음"으로 보고 라이브를 그대로 둔다. MediaMTX에 닿으면(목록을 받으면) 여전히 실제 송출에 맞춘다.
- **요청 분산**은 쿠버네티스 Service(NodePort, kube-proxy)가 준비된 파드 사이에 연결 단위로 나눈다. 세션이 DB에 있으므로 고정 세션(sticky session)이 필요 없다.

고려한 대안:

- **Postgres로 옮기기**: 노드가 여럿이어도 되고 동시 쓰기에 강하다. 그러나 sqlx 쿼리·마이그레이션을 모두 Postgres 문법으로 바꾸고 ⑥ 단일 VM에도 DB 서버를 더해야 한다. 이 과제의 범위(로컬 단일 노드 클러스터에서 스케일 아웃·인 확인)에 비해 크다.
- **채팅을 DB에 쓰고 폴링하기**: 저장하지 않던 채팅을 저장하게 되고 지연이 폴링 간격만큼 생긴다.
- **고정 세션으로 같은 파드에 붙이기**: 파드가 줄면 그 파드의 상태(메모리 채팅, 송출 세션 표)가 사라져 해결이 되지 않는다.

한계(다중 노드로 가려면 필요한 것): ReadWriteOnce 볼륨은 한 노드에서만 마운트되고, 네트워크 파일 시스템(ReadWriteMany) 위의 SQLite는 잠금을 믿을 수 없다. 노드가 여럿이면 DB를 Postgres 같은 DB 서버로, 녹화방송 영상을 오브젝트 스토리지(S3 호환)로 옮겨야 한다. MediaMTX는 송출 중인 영상을 메모리에 들고 있어 한 대로 두며, 여러 대로 늘리려면 채널(경로)마다 같은 MediaMTX로 보내는 설계가 따로 필요하다. Redis도 한 대이며 꺼지면 그동안 다른 인스턴스로 가는 채팅만 끊긴다.
